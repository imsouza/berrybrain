# BerryBrain v1.4.8 Whole-System Coherence, Ontology, and Maturity Plan

**Date:** 2026-08-14
**Status:** Software implementation complete; release validation in progress; external research gates remain open
**Target version:** 1.4.8
**Baseline revision:** `c297558` (`v1.4.7`) plus the current uncommitted graph repair work
**Scope:** Every product surface, persisted model, API contract, background workflow, AI path, graph semantic, operational control, test layer, and documentation claim
**Release state:** User authorized commit, push, tag, and release after all local release gates pass

## 1. Executive Decision

BerryBrain implements a **typed property graph with a formal ontology application profile**. The
profile includes a BerryBrain namespace, stable resource IRIs, Turtle vocabulary, SHACL shapes,
JSON-LD/Turtle export, provenance-bearing assertions, and validation tests. It is not a universal
domain ontology or a complete OWL reasoning system and must not be described as one.

The current graph has real operational semantics:

- node categories are validated;
- relationship types have procedural domain and range rules;
- active graph records carry evidence, provenance, calculated evidence scores, and external vocabulary mappings;
- semantic clusters assign context colors independently from node geometry;
- deletion feedback can suppress the exact rejected artifact and trigger scoped repair;
- graph data participates in retrieval and Ask context.

The current system still has explicit semantic boundaries:

- it does not provide a general-purpose OWL reasoner or a complete competency-question SPARQL suite;
- the service named HippoRAG remains a custom ontology-aware multi-hop sidecar, not the published
  HippoRAG algorithm;
- ontology constraints guide validation, retrieval, and serialization, but do not imply universal
  logical truth;
- Judge agreement is synthetic regression evidence and is not human calibration.

Current maturity is therefore classified as:

> **Engineering prototype with tested application-level graph contracts and incomplete representative evidence.**

It must not be classified as production-proven, statistically calibrated, autonomously
weight-trained, or superior to competing RAG systems until the corresponding gates in this plan
pass. The accurate learning claim is **feedback-guided, context-scoped policy adaptation**.

## 2. Direct Answers: Shapes, Colors, Edges, and Ontology

### 2.1 What each visual channel means

| Visual channel | Intended meaning | Current implementation | Required wording |
|---|---|---|---|
| Shape | Application node category | One geometry per node category, such as concept, entity, topic, note, insight, and source | `Shape = node category` |
| Fill color | Semantic context or cluster | Cluster palette for most nodes; note and insight have explicit display overrides | `Color = semantic context; notes and insights are highlighted` |
| Border | Contrast, selection, or artifact state | Palette border plus selection styling | `Border = interaction or state` |
| Edge arrow | Predicate direction | Directed except explicitly symmetric predicates | `Arrow = relationship direction` |
| Edge label | Relationship predicate | Internal relationship name and ontology property are available | `Label = relationship predicate` |
| Edge style | Relationship state and strength | Partially implemented; not yet governed by one canonical policy | `Style = assertion state; width/opacity = evidence score` |

Shape and color must remain independent. A concept remains a concept-shaped node even if its context changes. Nodes in the same semantic context may share a color while retaining distinct shapes.

The mandatory visual exceptions are:

- note nodes use BerryBrain primary red `#CC4168` as their displayed fill;
- insight nodes use a rectangular geometry and a distinct highlight treatment;
- semantic cluster membership remains stored separately, including for notes and insights, so context is not lost by the display override.

### 2.2 What edges must mean

An edge is not decorative proximity. It is an assertion with:

- a stable subject;
- one controlled predicate;
- a stable object;
- direction or an explicit symmetric declaration;
- source evidence;
- provenance;
- lifecycle state;
- quality-gate state;
- a calculated support score;
- a reason in English;
- creation and update timestamps;
- invalidation dependencies.

Layout distance may help reading, but it must never be interpreted as a semantic predicate. Cluster membership may influence layout, but it must never create an edge by itself.

### 2.3 What the ontology is for

The ontology must provide five concrete benefits:

1. **Data quality:** reject invalid node categories, invalid predicates, invalid direction, and invalid domain/range combinations.
2. **Retrieval precision:** let Ask and RAG distinguish a note mentioning a person from a person exemplifying a concept or a claim contradicting another claim.
3. **Explainability:** expose why a path exists and which evidence supports it.
4. **Interoperability:** export a stable graph that RDF and knowledge-graph tools can interpret without BerryBrain source code.
5. **Bounded inference:** derive only declared inverse, symmetric, hierarchy, and provenance relationships, with inferred facts separated from asserted facts.

The ontology must not be used as a marketing label for a list of node names. Its value is measurable only when semantic constraints improve graph precision, retrieval, answer faithfulness, maintenance, or interoperability.

## 7. Persisted Field Audit

This section covers every ORM model. Implementation must produce a machine-readable data dictionary containing column name, type, nullability, default, owner, source of truth, sensitivity, retention, validation, index, uniqueness, foreign key, cascade policy, and API exposure.

### 7.1 Content and derived knowledge fields

Models covered:

- `NoteRecord`
- `NoteAttachmentRecord`
- `AttachmentExtractionRecord`
- `TagRecord`
- `ConceptRecord`
- `GeneratedMetadataRecord`
- `ChunkRecord`
- `EmbeddingRecord`

Required field rules:

- note `path` is the canonical vault locator, normalized once and protected against traversal;
- note identity must survive rename and move through a stable UUID, not path alone;
- `content_hash` and note version must identify exactly which source generated each derivative;
- Markdown content and user-authored labels must be preserved verbatim, including language;
- system-generated metadata must be English;
- attachment filename, declared MIME, detected MIME, checksum, size, validation, extractor, and provenance must be independent fields;
- attachment extraction must have bounded size, time, CPU, and output limits;
- chunks must preserve source offsets and heading paths and become stale when the source hash changes;
- embeddings must bind provider, model, dimension, content hash, and normalization policy;
- `ConceptRecord` must be consolidated with `GraphNodeRecord` or assigned a clearly distinct role;
- generated metadata stored as text JSON must receive versioned JSON Schema validation or native JSON storage where supported.

Findings:

- [ ] Add a stable note UUID and derivative lineage key.
- [ ] Define one canonical concept store; remove duplicated concept semantics.
- [ ] Add foreign keys and scoped cascades for attachments, extractions, chunks, embeddings, and metadata.
- [ ] Prove file-vault and database convergence after create, edit, rename, move, external edit, delete, and restore.
- [ ] Add malformed and adversarial attachment fixtures.

## 10. Retrieval, RAG, and Graph Use

### 10.1 Current finding

The sidecar in `apps/hipporag` is not the published HippoRAG implementation. It currently provides:

- SQLite persistence;
- heuristic or optional Ollama-compatible OpenIE extraction;
- label-based triples;
- adjacency reconstruction;
- bounded breadth-first multi-hop traversal.

The official HippoRAG method combines LLM/OpenIE extraction, knowledge graphs, entity/fact recognition, and Personalized PageRank. BerryBrain must choose one of two honest paths:

1. Rename the current service to `graph-retrieval` and document its custom algorithm; or
2. Integrate and validate the official HippoRAG algorithm under a compatible license and benchmark it independently.

Until path 2 is complete, API fields, settings, docs, UI, reports, and release claims must not call the custom sidecar HippoRAG without the qualifier `compatible graph-retrieval sidecar`.

### 10.2 Current semantic limitations

- triples use labels as subject/object identity, so homonyms may collapse;
- ontology classes and properties are serialized strings, not validated RDF terms;
- no stable IRI survives rename;
- no formal reasoning uses ontology axioms;
- broad `related` edges can increase false multi-hop recall;
- quality-gate state is not consistently enforced before retrieval;
- graph retrieval metrics can reward paths that are structurally present but semantically wrong.

### 10.3 Target retrieval pipeline

1. Parse the user intent into content, graph-structure, ontology, comparison, gap, or provenance intent.
2. Build query entities and concepts without mutating the graph.
3. Retrieve lexical and dense chunk candidates.
4. Retrieve accepted graph paths under domain/range, quality, and freshness constraints.
5. Optionally execute bounded ontology inference from accepted facts.
6. Rerank passages and paths with calibrated evidence features.
7. Generate only from selected evidence.
8. Validate citations and claim entailment.
9. Return answer, evidence, graph paths, uncertainty, provider state, and retry/configuration actions.
10. Persist diagnostics without storing sensitive prompt content by default.

### 10.4 Retrieval invariants

- [ ] Deleted, stale, rejected, quarantined, or superseded artifacts never enter default retrieval.
- [ ] Labels are presentation values, never graph identity.
- [ ] Every answer claim maps to one or more source spans.
- [ ] No-evidence queries produce a clear abstention.
- [ ] Graph expansion cannot lower factual recall beyond the registered non-inferiority margin.
- [ ] Ontology-aware retrieval must beat the same graph without semantic predicates before claiming benefit.
- [ ] Query latency, provider cost, token use, and memory are recorded per retrieval strategy.

## 11. Confidence and Uncertainty

### 11.1 Current method

Active graph records use `jeffreys-wilson-evidence-v2`. The method:

- deduplicates named evidence signals;
- averages bounded continuous signal scores;
- applies a Jeffreys-smoothed mean;
- applies a Wilson interval formula using the number of signals as sample size.

This is calculated rather than a user-entered constant. However, its current statistical interpretation is not justified:

- heterogeneous evidence scores are treated like independent observations;
- each evidence item can contribute a perfect `1.0` signal merely by existing;
- signals from the same source may be correlated;
- the sample size is evidence-signal count, not repeated calibrated outcomes;
- the Wilson interval assumes a binomial-proportion interpretation that these continuous signals do not necessarily satisfy;
- current scores have not been calibrated against enough human-labeled truth outcomes.

Therefore the UI must call the current result an **evidence support estimate**, not a statistical confidence interval, until calibration passes.

### 11.2 Target score separation

| Score | Meaning | User editable |
|---|---|---|
| Evidence coverage | Fraction of material claims with cited support | No |
| Source quality | Versioned rubric result for cited sources | No |
| Entailment probability | Calibrated probability that evidence supports the assertion | No |
| Judge agreement | Agreement/dispersion among valid Judge roles | No |
| Cluster membership | Relative semantic membership and margin | No |
| Retrieval relevance | Query-specific ranking score | No |
| User acceptance | Observed feedback outcome, not truth probability | User action is input, aggregate is calculated |

### 11.3 Calibration plan

- [ ] Create a stratified human-labeled set of nodes, edges, insights, and answers.
- [ ] Include positive, negative, ambiguous, cross-domain, homonym, stale, and adversarial examples.
- [ ] Split calibration and evaluation sets by note/source to prevent leakage.
- [ ] Compare isotonic, Platt/logistic, beta, and uncalibrated scores.
- [ ] Report Brier score, log loss, expected calibration error, maximum calibration error, AUROC, AUPRC, and reliability diagrams.
- [ ] Report interval coverage only for a model that supports valid intervals.
- [ ] Version every formula, feature set, threshold, and calibration dataset.
- [ ] Return `null`/`unavailable` when evidence is insufficient.
- [ ] Never display `100%` from one unverified model output.
- [ ] Trigger scoped recalculation after accepted edit, delete, source change, Judge verdict, or evidence change.

## 12. Judge, Agents, Insights, and Feedback

### 12.1 Judge committee

The current default committee size is three with roles for faithfulness, relevance, and contradiction. Source-quality and ontology-consistency roles are available for larger committees. Runtime evidence shows three distinct models from one provider, but prior invalid model assignments produced repeated `GraphAIUnavailable` failures.

Required policy:

- provider catalog is refreshed and models are capability-tested before assignment;
- the generator model is excluded from Judge slots when alternatives exist;
- distinct models are required; distinct providers are preferred but not falsely guaranteed;
- same-provider operation is clearly disclosed;
- invalid or removed models make the committee `degraded`, not silently replaced;
- high-impact artifacts require deterministic structural validation plus enough valid Judge verdicts;
- position/order is randomized for pairwise evaluations;
- prompts defend against instruction injection from evaluated content;
- raw Judge score is not a calibrated probability;
- enforcing mode is blocked until human agreement gates pass.

### 12.2 Quality-gate state machine

```text
generated
  -> structurally_invalid -> quarantined
  -> structurally_valid -> pending_judge
  -> passed -> active
  -> review -> provisional_or_user_review
  -> insufficient_evidence -> quarantined
  -> rejected -> quarantined
  -> stale -> pending_recalculation
  -> superseded -> archived
```

Notes authored by the user remain visible as source artifacts, but AI-derived semantic assertions from them follow the gate. Default retrieval and default graph views include accepted artifacts plus user source notes, not rejected semantic assertions.

### 12.3 Continuous agents

Current "agents" are scheduled, durable workflows triggered by worker heartbeat and graph changes. They perform clustering, enrichment, Judge evaluation, and insight generation. They are not autonomous subagents continuously retraining a model.

Required terminology and behavior:

- call them maintenance agents only if each has an explicit goal, trigger, inputs, tools, output contract, budget, timeout, and audit record;
- otherwise call them background workflows;
- expose last run, next eligible run, current stage, ETA range, result, provider, and failure recovery;
- bound work by changed dependency scope;
- prevent multiple agents from repeatedly regenerating equivalent artifacts;
- evaluate each agent by precision, useful-change rate, cost, latency, and user reversal rate.

### 12.4 Insight lifecycle

- insights are generated automatically on the configured 1-168 hour interval, default 24 hours, and after relevant graph changes when the scheduler determines work is due;
- manual generation is a recovery or explicit refresh action, not the primary design;
- insights appear as graph nodes with evidence and accept/reject actions;
- insight records remain as lifecycle history, but a separate mandatory Insights page is optional;
- rejected insights must create feedback that prevents immediate equivalent regeneration;
- accepted insights may remain an accepted claim or become a permanent note through an explicit user action;
- notification volume is grouped per insight batch.

### 12.5 Feedback semantics

User deletion, editing, acceptance, and rejection produce durable feedback features:

- artifact signature;
- context signature;
- source-note IDs and versions;
- action;
- replacement payload if edited;
- timestamp;
- active/inactive feedback state;
- resulting scoped repair operation;
- later recurrence outcome.

This supports non-parametric behavioral adaptation. A future learned ranking model may use consented, anonymized feedback only after a documented dataset, privacy policy, offline evaluation, rollback mechanism, and drift monitoring exist.

## 13. Vault, Note, and Graph Lifecycle

### 13.1 Note creation

1. Create a real Markdown file and stable note UUID.
2. Open the note editor from every `New note` entry point.
3. Persist source and database record atomically or through a recoverable operation log.
4. Enqueue one idempotent pipeline root with the exact content hash.
5. Show stage, queue position range, elapsed time, ETA range, and recovery action.
6. Publish the note node immediately as a source artifact.
7. Publish derived nodes and edges only under the quality-state policy.

### 13.2 Note edit

1. Detect optimistic-concurrency conflict using base hash.
2. Save the new source version.
3. Mark derivatives bound to the previous hash stale.
4. Compute the impacted dependency subgraph.
5. Reparse, re-embed, re-extract, rejudge, recluster, regenerate affected insights, and resynchronize retrieval only for that scope.
6. Preserve accepted user annotations unless their subject was removed.
7. Archive superseded derivative versions for audit according to retention policy.
8. Show background progress without blocking continued editing.

### 13.3 Note rename or move

- Stable note identity does not change.
- Wikilinks and backlinks are updated or reported as unresolved according to explicit policy.
- Path indexes, FTS, graph metadata, attachment ownership, and RAG document identifiers update.
- No duplicate note node is created.
- Rollback restores both filesystem and database state.

### 13.4 Note deletion

1. Confirm scope and explain derived-data impact.
2. Create a tombstone or durable delete event.
3. Remove the source file according to configured trash/permanent-delete policy.
4. Invalidate chunks, embeddings, metadata, attachments, note node, incident edges, dependent insights, semantic profiles, cluster assignments, enrichments, research results, and RAG index records.
5. Recompute only affected clusters, neighbors, path scores, and insights.
6. Prevent stale jobs from recreating the note or its derivatives by checking note UUID and source version.
7. Return the UI to a valid workspace route and show repair progress.
8. Verify absence after process restart and browser refresh.

### 13.5 Generated node deletion

1. Persist context-scoped deletion feedback before removing active visibility.
2. Quarantine/tombstone the node immediately.
3. Quarantine incident edges and derived insights.
4. Remove semantic child records or bind them to archived node history under one policy.
5. Recompute affected clusters and retrieval projections.
6. Suppress equivalent regeneration in the same source/context unless new evidence materially changes the signature.
7. Return to the graph route and show scoped repair state.

### 13.6 Lifecycle acceptance gates

- [ ] Create/edit/delete/rename/move are idempotent under retry.
- [ ] A deleted artifact does not reappear after refresh, restart, rebuild, or sidecar resync.
- [ ] No stale job can write against a superseded content hash.
- [ ] No orphan derivative remains after retention cleanup.
- [ ] Scoped recomputation produces the same accepted graph as a clean full rebuild for the impacted fixture.
- [ ] User-visible ETA is a range derived from recent same-stage percentiles, not a fixed number.
- [ ] Every failure offers retry, configuration, or diagnostic navigation.

## 16. API and Contract Governance

### 16.1 Request validation findings

## 20. Database, Migration, and Recovery

### 20.1 Relational integrity plan

P0 migration sequence:

1. Create a verified backup and record checksum.
2. Generate an orphan report by every intended parent-child pair.
3. Classify orphan rows as deletable history, recoverable archive, or data-loss risk.
4. Remove/archive 380 verified graph-semantic orphans transactionally.
5. Add explicit parent keys and indexes.
6. Rebuild SQLite tables where required to add foreign keys and check constraints.
7. Enable `PRAGMA foreign_keys=ON` on every connection and test it.
8. Add unique constraints for natural idempotency keys and stable UUIDs.
9. Run integrity, foreign-key, duplicate, and semantic audits.
10. Restore the pre-migration backup in an isolated instance and prove rollback.

## 28. Academic Research Proposal

### 28.1 Candidate themes

1. **Ontology-constrained graph-augmented retrieval for local-first personal knowledge systems.**
2. **The effect of typed semantic relationships and quality gates on multi-hop RAG precision.**
3. **Human feedback as non-parametric graph maintenance in AI-assisted personal knowledge bases.**
4. **Calibration and reliability of multi-model LLM Judges for automatically extracted knowledge graphs.**

Recommended primary theme:

> **Evaluating ontology-constrained Graph RAG with human feedback in a local-first personal knowledge system.**

### 28.2 Research questions

- RQ1: Does a typed and SHACL-validated graph improve multi-hop retrieval over lexical, dense, hybrid, and untyped-graph baselines?
- RQ2: Do Judge quality gates improve relation precision without unacceptable recall and latency loss?
- RQ3: Does durable user feedback reduce recurrence of semantically irrelevant nodes and edges after later graph updates?
- RQ4: How well do calculated uncertainty scores predict human acceptance and factual correctness?
- RQ5: What cost, latency, privacy, and usability tradeoffs arise from local-first graph enrichment?

### 28.3 Hypotheses

- H1: Typed accepted-graph retrieval improves multi-hop Recall@10 and MRR over hybrid RAG on representative multi-hop questions.
- H2: Ontology and Judge gates reduce false cross-domain edges and unsupported answer claims.
- H3: Feedback-aware scoped repair reduces recurrence of rejected artifact signatures relative to a no-feedback ablation.
- H4: Calibrated support estimates have lower Brier score and expected calibration error than raw model/Judge scores.
- H5: Scoped recomputation lowers freshness latency and provider cost without changing accepted impacted-subgraph output relative to full rebuild.

### 28.4 Mixed-method design

Quantitative:

- internal A0-A9 ablations;
- external RAG/GraphRAG/HippoRAG baselines;
- human-labeled node, edge, insight, and answer evaluation;
- performance, cost, and reliability experiments;
- calibration and error analysis.

Qualitative:

- moderated task sessions;
- semi-structured trust and usefulness interviews;
- thematic analysis of deletion/edit/acceptance decisions;
- audit of why users reject semantically plausible but contextually irrelevant artifacts.

### 28.5 Ethics and reproducibility

- obtain informed consent for user studies;
- minimize and anonymize collected note content;
- allow participant withdrawal and data deletion;
- do not publish personal vault data;
- document model/provider terms and remote data flow;
- preregister the confirmatory protocol where feasible;
- publish code, synthetic fixtures, public-dataset adapters, raw non-sensitive metrics, analysis scripts, and environment manifest;
- state all conflicts, limitations, and negative results.

### 28.6 Thesis artifact structure

1. Problem and research questions.
2. Personal knowledge management and RAG background.
3. Knowledge graphs, RDF, SKOS, OWL, SHACL, and provenance.
4. BerryBrain architecture and threat model.

## 34. Final Audit Position

The colors, shapes, and edges now have an intended coherent division of responsibility, but that visual coherence must not be confused with formal semantic maturity.

- Shapes identify application node categories.
- Colors identify semantic context, with deliberate note and insight display overrides.
- Edges identify typed assertions and must carry direction, evidence, provenance, lifecycle, and quality.
- The ontology should validate, explain, interoperate, and improve retrieval.
- The current implementation has a formal BerryBrain ontology application profile and remains
  intentionally narrower than a universal domain ontology or complete OWL reasoning system.
- User actions drive auditable feedback-guided policy adaptation across agents and Judges; they do
  not silently train model weights.

The engineering release closes the accepted-graph coherence work: one state policy, rejected
artifact exclusion, orphan repair, provider/Judge validation, bounded uncertainty language,
ontology mappings, and qualified custom-sidecar naming. The remaining maturity work is empirical:
human calibration, longitudinal learning outcomes, same-corpus external comparison, accessibility
evidence, and independent replication.
